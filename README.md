# Jev Inspect — Есть дефект или нет

Прототип для репетиционного трека Hackalem AI: программа принимает изображение,
передаёт его текстовое представление модели Jev от TypeSafe AI и выводит
**`OK`** или **`DEFECT`**. В терминале отображаются путь к файлу, индикатор
ожидания, цветной результат и измеренное время запроса.

> **Ограничение:** Jev принимает только текст. Изображение преобразуется в сетку
> 64×64 с десятью уровнями яркости. Это эксперимент для простых фигур, а не
> готовая система промышленного контроля. На `test 3.png` обнаружен пропуск:
> тонкая белая линия исчезает при преобразовании, и модель получает такое же
> представление, как для пустого `test 2.png`.

## Установка

Требуется **Python 3.10 или новее** и доступ к репозиторию.

```bash
git clone https://github.com/BAITC-Hacks/hack-0a99e361-xy.git
cd hack-0a99e361-xy
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
cp .env.example .env
```

В Windows вместо команды `source` используйте `.venv\Scripts\activate`.
В PowerShell скопировать шаблон можно командой `Copy-Item .env.example .env`.

## Настройка API-ключа

1. Войдите в [консоль TypeSafe AI](https://console.typesafe.ai/home).
2. Откройте [раздел API-ключей](https://console.typesafe.ai/settings/keys)
   и создайте ключ для своего аккаунта.
3. В локальном `.env` замените значение-заглушку:

```dotenv
TYPESAFE_API_KEY=your_actual_key
TYPESAFE_MODEL=jev-latest
```

Программа читает `.env` рядом с `detect.py`. Переменные окружения имеют приоритет.
Настоящий ключ не входит в репозиторий: `.env` исключён через `.gitignore`.

Официальный пакет называется
[`typesafe-sdk`](https://docs.typesafe.ai/sdk/python), импорт — `typesafe_sdk`.
Пакет [`typesafe-ai`](https://pypi.org/project/typesafe-ai/) включён по условию
задания, но является неофициальной обёрткой, устанавливающей официальный SDK.
Приложение импортирует официальный SDK напрямую.

## Запуск

Создать примеры и проверить их:

```bash
python generator.py
python detect.py ok.png
python detect.py defect.png
```

Генератор перезаписывает `ok.png` и `defect.png`. Для отдельной папки:

```bash
python generator.py --output-dir samples
```

Проверить собственные рисунки; пути с пробелами заключайте в кавычки:

```bash
python detect.py "test 1.png"
python detect.py "test 2.png"
python detect.py "test 3.png"
```

Путь, индикатор ожидания, цветная плашка, версия модели и время запроса идут
в **stderr**. При успешном запросе **stdout** содержит только `OK` или `DEFECT`
с переводом строки. Для использования в других программах:

```bash
python detect.py ok.png --plain > result.txt
```

Флаг `--plain` скрывает оформление успешного результата, но не сообщения об
ошибках. Время измеряется вокруг вызова SDK и включает сеть, повторные попытки
и проверку ответа. Задержка менее секунды не гарантируется.

## Как это работает

1. Программа проверяет PNG, JPEG или WebP: до 10 МиБ, до 16 мегапикселей,
   только один кадр. Учитывает EXIF-ориентацию и накладывает прозрачность на белый фон.
2. Сохраняя пропорции и добавляя поля, уменьшает изображение до 64×64.
   Используется усреднение `BOX`: оно не добавляет полосы и ореолы, которые
   могут выглядеть как повреждения.
3. Яркость каждого пикселя кодируется цифрой от `0` до `9`.
   Эта сетка передаётся как структурированное поле `state`. Имя файла,
   метаданные и ожидаемая метка не отправляются.
4. Официальный SDK вызывает `POST https://api.typesafe.ai/v1/systemone`.
   Вопрос типа **Choice** ограничивает варианты ответа значениями `OK` и `DEFECT`.
5. Pydantic проверяет метку, тип ответа, наличие обеих вероятностей, их сумму
   и допустимый диапазон уверенности. Неожиданные поля решения отклоняются.
6. В stdout печатается выбор модели. Локального правила, назначающего класс
   по имени файла, числу пикселей или порогу повреждений, нет.

Текущий запрос описывает **тёмный заполненный квадрат на белом фоне**.
Целый квадрат соответствует `OK`, трещины, отверстия и сколы — `DEFECT`.
Пользовательские рисунки на чёрном фоне отличаются от этого сценария, поэтому
их успешная классификация сама по себе не подтверждает универсальность решения.

Base64 не добавляет зрение текстовой модели. Здесь используется документированный
интерфейс структурированного состояния, а не неподдерживаемая отправка `image_url`.
Подробнее: [форматы входных данных](https://docs.typesafe.ai/concepts/state)
и [справочник API](https://docs.typesafe.ai/api).

## Почему TypeSafe AI?

Jev — модель **System One**, предназначенная для узких решений внутри программ.
Примитив Choice возвращает выбранный класс, вероятности и уверенность; не нужно
извлекать ответ из произвольного текста.
[Описание примитивов](https://docs.typesafe.ai/introduction).

Строгий контракт результата гарантирует допустимую форму ответа, но не правильность
классификации и не идентичность всех повторных ответов. Для воспроизводимой оценки
можно указать конкретную доступную версию в `TYPESAFE_MODEL`: псевдоним
`jev-latest` со временем меняется.
[Версии моделей](https://docs.typesafe.ai/models).

TypeSafe сообщает о быстром принятии решений в
[анонсе Jev](https://typesafe.ai/blog/introducing-system-one-models-and-jev).
Программа показывает фактическую задержку запроса в вашей среде.
Для изображений Jev здесь выступает слоем принятия решения после подготовки
данных; собственного визуального входа у него пока нет.

## Проверки

Без API-ключа и сетевых запросов:

```bash
python test_detect.py
```

Результат последнего запуска:

```text
PASS: 30 offline checks (real SDK, mocked HTTP; no live accuracy test).
```

Проверяется реальный SDK с подменённым HTTP-транспортом: формат запроса,
точный stdout, неправильные ответы, повторные попытки, ошибки авторизации,
тайм-ауты, недопустимые изображения и отсутствие искусственных полос
на однородном квадрате. В некоторых ответах метки намеренно переставлены,
чтобы проверить, что решение действительно приходит из API.
**Эти проверки не измеряют точность модели.**

### Реальные запросы к API — 21 сентября 2026 года

Использовался `jev-latest`, который разрешился в `jev-1.13.0`.

| Изображение | Содержимое | Ответ API | Время запроса |
| --- | --- | --- | --- |
| `ok.png` | Целый квадрат | `OK` | 911,4 мс |
| `defect.png` | Квадрат со сколом и трещиной | `DEFECT` | 1 323,0 мс |
| `test 1.png` | Белые линии на чёрном фоне | `DEFECT` | 973,5 мс |
| `test 2.png` | Пустой чёрный фон | `OK` | 955,8 мс |
| `test 3.png` | Короткая тонкая белая линия | `OK` | 2 287,3 мс |

Если белую линию считать повреждением, результат `test 3.png` — **пропущенный
дефект**. Проверка показала: его текстовая сетка полностью совпадает с сеткой
`test 2.png` — различающихся пикселей **0**. Линия теряется при уменьшении
и квантовании яркости; модель не получает информации о ней.
Этот известный недостаток пока не исправлен.

Результаты отдельных запусков не являются оценкой общей точности или гарантией
задержки. Для работы с реальными фотографиями нужна подготовка данных,
сохраняющая мелкие и цветовые дефекты, и проверка на независимом размеченном наборе.

## Ошибки и коды завершения

| Код | Значение |
| --- | --- |
| `0` | Получено и напечатано проверенное решение API |
| `1` | Ошибка изображения или API; stdout пуст |
| `2` | Отсутствует или некорректен ключ либо аргументы командной строки |
| `130` | Обработка прервана пользователем |

Тайм-аут запроса — 10 секунд; SDK выполняет не более двух повторных попыток
с бюджетом повторов 30 секунд. Ошибки авторизации не повторяются.
Тела ошибочных ответов сервера не выводятся, чтобы не раскрывать переданные данные.
Сбой API или некорректное изображение не превращаются в выдуманный `OK`/`DEFECT`.
